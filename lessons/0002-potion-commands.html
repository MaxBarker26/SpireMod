2. Find the activation method

Both potions override this game-defined method:

protected override async Task OnUse(
    PlayerChoiceContext choiceContext, Creature? target)

OnUse is the extension point for this potion's effect. PotionModel.OnUseWrapper calls it as part of a larger sequence that removes the consumed potion and runs surrounding potion hooks. Your subclass supplies the effect inside that sequence.

Compare these excerpts from the two OnUse bodies. Visual effects have been omitted; the command calls and target checks are preserved.

EnergyPotion

PotionModel.AssertValidForTargetedPotion(target);
await PlayerCmd.GainEnergy(
    DynamicVars.Energy.BaseValue, target.Player);

SwiftPotion

PotionModel.AssertValidForTargetedPotion(target);
await CardPileCmd.Draw(
    choiceContext, DynamicVars.Cards.BaseValue, target.Player);

Both declare TargetType.AnyPlayer and PotionUsage.CombatOnly. Here target.Player is the recipient; Owner is the potion's owner. They need not be the same player. The check rejects a null target; validity checks elsewhere govern which targets can be selected.

choiceContext is passed through to drawing so the operation can handle player choices. Keep that context when composing behavior. The awaited calls let each operation complete before execution proceeds.

For now, read DynamicVars.Energy.BaseValue as “the potion's configured energy amount.” These game potions define amounts with EnergyVar(2) and CardsVar(3). We will cover dynamic variables and their relationship to text when defining your own potion.

3. Follow one command deeper

Inspect PlayerCmd.GainEnergy. Before modifying the player's combat energy, it calls Hook.ModifyEnergyGain and Hook.AfterModifyingEnergyGain. Directly changing an energy property would bypass this command's processing.

Likewise, CardPileCmd.Draw delegates to DrawInternal, which checks draw prevention, respects the hand limit, shuffles when necessary, and records and signals draws. Moving a card straight into the hand is not the same operation.

Transferable pattern: content model → lifecycle override → awaited game commands. Use the same investigation process for a card, relic, or power; find the appropriate lifecycle method and operations for that content.

4. Notice the boundary of “until full”

The installed game exposes CardPile.MaxCardsInHand (currently 10) and the hand's Cards.Count. Use the named game limit rather than assuming a literal number in your own behavior.

A draw request can return fewer cards than requested, including zero. Draw prevention, exhausted supplies, a full hand, or combat ending can stop it. An unchecked while (handNotFull) loop could keep requesting a draw that never succeeds.

Later we will choose a bounded implementation and define how it behaves if draw-triggered effects change the hand. Today, the key is to distinguish a requested draw count from guaranteed cards drawn.
